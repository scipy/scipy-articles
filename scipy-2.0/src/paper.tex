\section{Support for Graphics Processing Units (GPUs) and Just-in-Time (JIT) Compilation
Through the Python Array API Standard}

Thanks to NumPy's success~\cite{Harris2020} in unifying the two early array packages for
Python, Numeric~\cite{Dubois1996,ascher2000numerical} and
numarray~\cite{Greenfield2003numarrayA}, for most of its existence,
SciPy's functionality has been built on top of NumPy arrays. However, driven in part
by the boom in machine learning and artificial intelligence, graphics
processing units (GPUs) have become an
important tool for scientific computing. Likewise, just-in-time (JIT) compilation
and automatic differentiation are becoming more common in
scientific workflows. This posed a problem for SciPy, as while NumPy has been the de
facto standard for array computing in Python, it does not support GPUs, JIT compilation,
or automatic differentiation. This has led to the proliferation of other array packages
for Python, such as CuPy~\cite{cupy_learningsys2017}, JAX~\cite{jax2018github}, and
PyTorch~\cite{Ansel2024}, which fill these gaps. This has effectively led to a
dichotomy: SciPy cannot utilize the new features offered by these array packages, and
these new array packages cannot make full use of the large amount of functionality
SciPy provides.

Addressing this fragmentation using the Python array API standard~\cite{Meurer2023} has been a
major focus of SciPy 2.0. The standard defines standardised application
programming interfaces (APIs) and behaviours for arrays and
associated operations. Most importantly for SciPy, this enables
``array-consuming libraries to accept and operate on arrays from multiple different
array libraries''~\cite{Meurer2023}. In principle, by rewriting SciPy's functionality
in terms of these standardised APIs, SciPy can support any array package that
implements the standard. One caveat to this NumPy, CuPy, JAX, and PyTorch all predate
the standard\footnote{The first version of the Python array API standard was released
in December 2021, with new revisions appearing annually.} meaning they themselves are not
fully compliant. To resolve this, the array-api-compat package provides a lightweight
wrapper around these libraries to make them compliant with the standard. Likewise,
some functionality is not covered by the standard for a variety of reasons so the
array-api-extra package provides generic implementations of these operations.
Listings~\ref{lst:fiedler} shows how a typical Python function is rewritten
to support the standard.

While the recipe shown in Listing~\ref{lst:fiedler} can be applied to most of SciPy's
Python code, a significant amount of SciPy's functionality is implemented in Cython
and C/C++. This is typically the case when a Python implementation would not provide
satisfactory performance, such as when it is not possible to write the code in terms
of vectorised array operations. This presents a challenge as this means that these
functions cannot be converted by simply rewriting them in terms of standardised APIs.
SciPy has adopted to three approaches to address this.
The first, and simplest, is that if the array is stored on the CPU, then we can convert
it to a NumPy array, perform the computation, and then convert the result back to the
original array type. However, this approach is not feasible for arrays stored on the
GPU, due to the overhead of transferring data between the CPU and GPU. The second
approach uses the fact that array libraries such as JAX and CuPy have reimplemented
a subset of SciPy's functionality, in which case we \emph{delegate} to their
implementation. We also delegate for Python functions under the assumption that a
native implementation provides better performance than a generic implementation.
The final approach is to maintain two code
paths, the original compiled code path for NumPy arrays, and a new Python code path
written in terms of standardised APIs. While this allows SciPy to add support for
alternative array types, it does so at the cost of code duplication and increased
maintenance burden. Hence, this approach is used sparingly in situations when
maintaining two code paths brings a significant performance benefit. For example,
when executed on a GPU a Python implementation can outperform a compiled code
implementation executed on the CPU --- see \todo{Forward ref}. In the future,
SciPy also hopes to utilise the DLPack~\cite{dlpack}, which is an open in-memory
structure for sharing tensors among frameworks.

While enabling users to use SciPy with their preferred array types is a significant
advancement in and of itself, it can also offer significant performance benefits.
We will demonstrate this through a series of benchmarks covering the different
approaches for adopting array API standard, as previously discussed. All benchmarks
were executed on an Intel Core Ultra 7 165H and
an NVIDIA GeForce RTX 2050. Code to reproduce the benchmarks is available at
\href{https://github.com/scipy/scipy-articles}{github.com/scipy/scipy-articles}.

The first benchmark considers computing the sample skewness
$\gamma_1 = \mu_3/\mu_2^{3/2}$, where $\mu_i$ is the biased sample $i$th central
moment, using \texttt{scipy.stats.skew}.
This is a function which is implement purely
in Python so was converted to the array API standard by rewriting in-terms of
standardised function, similar to the example in Listing~\ref{lst:fiedler}.
Specifically, the benchmark considers
computing the skewness of three samples of size $n$ drawn from the gamma (with shape
and scale parameters 5 and 0.5), standard normal, and
beta distributions (with shape parameters 0.5 and 0.5). The computation is performed in
a vectorised fashion, i.e. only one call to \texttt{scipy.stats.skew} is made.

the aim of this being to maintain satisfactory performance for NumPy arrays while
also enabling support for other array types. The benchmark considers converting a
